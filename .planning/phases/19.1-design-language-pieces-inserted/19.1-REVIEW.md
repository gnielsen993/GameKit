## Summary

Reviewed the 28 listed files at HEAD `4fb12e6` on branch `2.0` against diff base `eb0839b`. This was a static review: no build, no tests and no simulator were run (another process owns them), so every behavioral claim below is derived from reading the code and from documented SwiftUI API semantics, not from observation. Findings about `KeyframeAnimator` rest on its documented behavior that a trigger change mid-animation restarts with freshly generated keyframes.

No blocker was found. Seven warnings and nine info items.

What held up under attack:

- **DEBUG near-win fixture, Release reachability.** `SudokuNearWinFixture.swift`, `SudokuViewModel+DebugFixture.swift` and `SudokuViewModel+TestSeam.swift` are wholly inside `#if DEBUG`. The four call sites (`SudokuViewModel.swift:313-315`, `SudokuViewModel+Outcome.swift:23-28` and `60-66`, `SudokuViewModel+SaveState.swift:73-77` and `103-106`, `SudokuGameView+DebugTuning.swift:15-19`) are each guarded, and `DEBUG` is defined only for the Debug configuration (`project.pbxproj:369`). Release gets a nil action and no fixture symbol.
- **Fixture, real data.** The only two `GameRecord` writers in Sudoku (`recordWin`, `recordGameOver`) both skip a fixture game. The only writer of the save slot (`saveCurrentState`) and the only remover (`clearSavedState`) both return early. Every other path I traced (restart, keep solving, hint request, mode and difficulty change, game over, practice completion) goes through those four functions. A real saved puzzle is neither overwritten nor deleted by a fixture game.
- **Tokens.** No hard-coded color, numeric `cornerRadius:` or numeric `.padding()` in any added line. The new black literals are confined to `Core/SurfaceDepth.swift`, which is the documented exemption.
- **Motion gates.** Press travel, the placement pop, the pill thumb, the end-card pre-roll and transition, and the count-up all read both the animations setting and Reduce Motion. The exception is WR-04.
- **Piece hit region.** `contentShape(Rectangle())` is applied after the bottom padding and outside the offset (`PieceButtonStyle.swift:71-78`), so it is the un-offset frame including the edge, as DESIGN.md 3.8 requires.
- **Equal, slower and assisted wins** return `setBestTime: false` (`GameStats.swift:101`, `284-289`), and the card reads nothing else (`SudokuEndStateCard.swift:108`).

The concerns are the two ways the personal-best badge can still be wrong (WR-01, WR-02), three ripple defects (WR-03, WR-04, WR-05), and three places the code departs from DESIGN.md 3.8 (WR-06).

## Warnings

### WR-01: The personal-best claim is compared against an arbitrary BestTime row

**File:** `gamekit/gamekit/Core/GameStats.swift:280-289`
**Issue:** `evaluateBestTime` fetches every `BestTime` for the game and difficulty with no sort and compares the new time against `existing.first`. `BestTime.swift:5-21` states that one-row-per-pair is enforced only by this write path, with no unique constraint because CloudKit rejects them. Two devices that each won before syncing therefore each inserted a row, and after sync both rows exist on both devices; `StatsExporter.swift:29-34` also imports envelope rows verbatim. Nothing in `Core/`, `App/` or `Screens/` de-duplicates them. With rows of 300s and 200s, a 250s win that happens to be compared against the 300s row returns `RecordResult(setBestTime: true, previousBest: 300)` and the card shows "Your best Easy time" while a faster 200s row stands. The fetch logic predates this phase, but until now its only effect was which row got mutated; this phase turned it into a user-facing claim.
**Fix:** Compare against the fastest row and keep every duplicate in step, without deleting anything (CLAUDE.md 1, data safety):
```swift
let existing = try modelContext.fetch(descriptor)
guard let previous = existing.map(\.seconds).min() else {
    modelContext.insert(BestTime(gameKind: gameKind, difficulty: difficulty,
                                 seconds: seconds, achievedAt: .now))
    return RecordResult(setBestTime: true, previousBest: nil)
}
guard seconds < previous else {
    return RecordResult(setBestTime: false, previousBest: previous)
}
for row in existing where row.seconds > seconds {
    row.seconds = seconds
    row.achievedAt = .now
}
return RecordResult(setBestTime: true, previousBest: previous)
```
Add a `RecordResultTests` case with two rows for one pair. `SudokuStatsCard.swift:84-86` has the same `first(where:)` read and should take the minimum too.

### WR-02: A win on a retried or restarted puzzle sets a best and claims the badge

**File:** `gamekit/gamekit/Games/Sudoku/SudokuViewModel+Outcome.swift:67-74`
**Issue:** `GameStats.swift:96-99` states the rule: "replaying a board you already lost is not comparable to a first solve", carried by `countsTowardRecords`. Minesweeper passes it (`MinesweeperViewModel+Persistence.swift:69`) and Math Crossword persists it. Sudoku never does. After a Lives-mode loss, "Retry this puzzle" (`SudokuGameView.swift:183`) calls `restart()` (`SudokuViewModel.swift:259-270`), which zeroes the clock, mistakes and `assistsUsed` and replays the same puzzle. Winning that run reaches `recordWin()` with `assistCount: 0` and the default `countsTowardRecords: true`, so it writes a `BestTime` and the card says "Your best <difficulty> time" for a board the player has already worked through once. The toolbar Restart does the same mid-game, and because `restart()` resets `assistsUsed`, a puzzle on which hints were taken can be restarted and won "unassisted". The card's own copy treats post-loss play as unranked ("Your ranked run ended when the hearts ran out."). Recording this way predates the phase; the explicit claim is new.
**Fix:** Track the replay in the view model and pass it through:
```swift
// SudokuViewModel
var countsTowardRecords = true          // reset to true in loadFreshPuzzle only

func restart() {
    clearSavedState()
    guard let puzzle = currentPuzzle else { return }
    let replay = state != .idle          // anything already started is a replay
    resetSessionState()
    countsTowardRecords = countsTowardRecords && !replay
    ...
}

// recordWin()
lastWinRecord = try? gameStats?.recordReportingBest(
    ..., assistCount: assistsUsed, countsTowardRecords: countsTowardRecords)
```
Persist the flag in `SudokuSaveState` (additive optional field, as `assistsUsed` was) so closing the app does not reset it. If retried wins are meant to count in Sudoku, say so in DESIGN.md 3.6 next to the badge rule instead.

### WR-03: The ripple starts from the selected cell, not from the cell that was placed

**File:** `gamekit/gamekit/Games/Sudoku/SudokuBoardView.swift:66-71`
**Issue:** The wave origin is `viewModel.selected`. That equals the placed cell only for pad input. `applyHint()` (`SudokuViewModel.swift:478-486`) commits at `hint.step.row/column` and `applyFallbackHint()` (`490-504`) commits at the first empty cell; neither changes the selection, and `requestHint()` does not select the hinted cell either. When "Fill it in" or "Reveal one square" completes a unit or wins the game, the ripple radiates from wherever the selection happens to be, or from the top-left cell when nothing is selected (`origin ?? 0`). That breaks the rule the code cites for itself ("so the wave reads as caused by the move", `SudokuCompletionWave.swift:52-53`).
**Fix:** Record the placement in the view model and use it as the origin:
```swift
// SudokuViewModel
private(set) var lastPlacedIndex: Int?   // set in commitValue for both modes,
                                         // cleared in resetSessionState

// SudokuBoardView.cellGrid
let origin = viewModel.lastPlacedIndex
```
Extend `SudokuCompletionWaveTests` with a hint-placed completion whose selection is elsewhere.

### WR-04: Changing Reduce Motion while a won board is on screen replays the whole-board ripple

**File:** `gamekit/gamekit/Games/Sudoku/SudokuCellView.swift:55-70`
**Issue:** The gate is inside the trigger expression: `trigger: motion ? waveCount : 0` and `trigger: motion ? shakeCount : 0`. `waveCount` is `completionGlowCount &+ winCount` and `winCount` is never reset, so after any win it is non-zero. When `motion` flips, the trigger value changes (N to 0, or 0 to N) and both animators fire with the current props. While `state == .won`, every cell has a non-nil `waveStep` (`SudokuBoardView.swift:69-71`), so the full accent-fill and 1.08 scale ripple plays across 81 cells. The realistic path: the player wins, sees the ripple, switches to iOS Settings or Control Center, turns Reduce Motion on, and returns to the win card or the viewed board. The ripple then plays once more at the moment they asked for it to stop. The in-app Animations toggle cannot reach this (Settings is a sheet off Home), but Reduce Motion can.
**Fix:** Keep the trigger independent of the gate and gate what the keyframes do, so a flip never fires anything and a gated trigger runs flat values:
```swift
KeyframeAnimator(initialValue: SudokuWaveValues(), trigger: waveCount) { values in
    cellBody(values)
} keyframes: { _ in
    SudokuCellFeedback.waveKeyframes(step: motion ? waveStep : nil)
}
.keyframeAnimator(initialValue: 0.0, trigger: shakeCount) { view, dx in
    view.offset(x: dx)
} keyframes: { _ in
    SudokuCellFeedback.shakeKeyframes(active: motion && isWrongFlashing)
}
```

### WR-05: A second completion within about a second hard-cuts the ripple still running

**File:** `gamekit/gamekit/Games/Sudoku/SudokuCellFeedback.swift:54-69`
**Issue:** Each new trigger regenerates keyframes for all 81 cells, and the `keyframes` closure ignores the current interpolated value it is handed (`SudokuCellView.swift:60`, `{ _ in ... }`). A cell that is part of the running wave but not of the new one gets the non-live track, whose first keyframe is `LinearKeyframe(0, duration: 0.001)`: its fill and scale snap from mid-rise to flat in one millisecond. A unit ripple lasts up to 1.06s, and the endgame is exactly where a player places the last few singles in quick succession, each completing a row, column or box. Each ripple is cut off by the next rather than finishing. `completionGlowIndices` is likewise replaced, not merged (`SudokuViewModel+CompletionFeedback.swift:27`).
**Fix:** Let a cell that is mid-flight finish its fall instead of snapping. Pass the current value through and start the non-live track from it:
```swift
} keyframes: { current in
    SudokuCellFeedback.waveKeyframes(step: motion ? waveStep : nil, from: current)
}

// waveKeyframes: for a non-live cell with current.fill > 0, skip the 1ms hold
// and ease from the current value to rest over `fall`.
```
Alternatively merge the steps of a wave that has not finished into the new step map so both run to completion.

### WR-06: Three places where the code departs from DESIGN.md 3.8

**File:** `gamekit/gamekit/Games/Sudoku/SudokuGameView+VideoMode.swift:236-251`
**Issue:** DESIGN.md is the tiebreaker and 3.8 is the spec this phase wrote.
1. "Video Mode uses compact pieces" and the sizes table gives compact to "Video Mode controls and pad". In both small-zone layouts `smallZoneModePillRow` builds `SudokuModePill` without `compact: true` and uses `eraseButton`, the regular 36pt circle, while the pad directly below is `.compact` (`SudokuGameView+VideoMode.swift:280`, `323`). One screen mixes 4pt and 2.5pt edges.
2. "Disabled pieces sit flat on their edge: no travel, dimmed". The mode pill is disabled in terminal states (`SudokuModePill.swift:52`) and sits flat, but nothing dims it; erase and the pad beside it drop to 0.4 opacity. After "View board" the pill is the one control that still looks live.
3. "Labels are rounded: pad digits, mode pill labels, titles and primary buttons only", and D-06 keeps captions regular. The best badge is a rounded caption (`SudokuEndStateCard.swift:126`) and `PieceCTAButton` rounds the secondary action too (`PieceCTAButton.swift:45`).
**Fix:** For 1, pass `compact: true` to the pill and use `SudokuEraseButton(..., compact: true)` in `smallZoneModePillRow`, or amend the 3.8 table to say small zones keep regular controls. For 2, add `.opacity(isInteractive ? 1 : 0.4)` to `SudokuModePill` (or dim inside `PieceButtonStyle` when `!isEnabled` so every caller gets it, and drop the per-caller opacity). For 3, either use `theme.typography.caption.weight(.bold)` for the badge or widen the sentence in 3.8 to "badges and call-to-action buttons".

### WR-07: Impossible-state guard: TimelineView pause flag that is always false

**File:** `gamekit/gamekit/Games/Sudoku/SudokuCountUpTime.swift:40`
**Category:** necessity
**Issue:** `TimelineView(.animation(minimumInterval: nil, paused: finished))` sits inside `if motion && !finished` (line 39). In that branch `finished` is false by construction, so `paused:` is always false; the moment `finished` becomes true the branch is replaced by the static text and the timeline no longer exists. The guarded state (a paused timeline that is still on screen) cannot occur.
**Fix:** Use `TimelineView(.animation)` and let the `if` be the only switch.

## Info

### IN-01: The DEBUG fixture fabricates the best-time claim, and the UI test asserts the fabrication

**File:** `gamekit/gamekit/Games/Sudoku/SudokuViewModel+Outcome.swift:60-66`
**Issue:** A fixture win sets `lastWinRecord = RecordResult(setBestTime: assistsUsed == 0, previousBest: nil)` without asking `GameStats`. It is DEBUG-only and deliberate, but it re-derives the assist rule that `RecordResult.swift:5-8` says callers never re-derive, and `PiecesSudokuTests.swift:123-124` asserts the badge exists on that fake. No automated check shows the badge absent on screen for a slower or assisted win, and every fixture screenshot carries the badge, so the no-badge layout is never looked at.
**Fix:** Add a read-only `GameStats.wouldSetBestTime(gameKind:difficulty:seconds:assisted:)` and have the fixture use it, or add a second launch argument that forces `setBestTime: false` and a UI test asserting the badge is missing.

### IN-02: A fixture game outlives the fixture, and applying it leaves stale session state

**File:** `gamekit/gamekit/Games/Sudoku/SudokuViewModel+DebugFixture.swift:26-73`
**Issue:** DEBUG only. `restart()` keeps `currentPuzzle`, so after Restart the player has a full ordinary puzzle that still carries the `-debug-near-win` id: it never saves and a win on it is never recorded, with nothing on screen saying so. Applying the fixture from the menu also leaves `undoSnapshot`, `activeHint`, `isHintCardVisible`, `interactionMode` (a UI test in Notes mode would toggle notes instead of placing) and `lastWinRecord` as they were.
**Fix:** In `applyNearWinFixture()` clear those fields, and in `restart()` under `#if DEBUG` re-apply the fixture or strip the suffix.

### IN-03: `RecordResult.previousBest` has no reader in the app

**File:** `gamekit/gamekit/Core/RecordResult.swift:22`
**Issue:** It is written at `GameStats.swift:287`, `289`, `298` and read only by tests. D-13 asked for it, so it is not speculative, but nothing shows "beat 4:32" yet.
**Fix:** Leave it if Phase 20 uses it; otherwise remove it with its tests.

### IN-04: The win card truncates the time and Stats rounds it

**File:** `gamekit/gamekit/Games/Sudoku/SudokuWinTime.swift:25`
**Issue:** `SudokuWinTime.string` uses `Int(seconds)`; `SudokuStatsCard.swift:91` uses `Int(s.rounded())`. A 250.6s win is "4:10" under the badge "Your best Easy time" and "4:11" as the best on the Stats screen.
**Fix:** Use one formatter for both; `SudokuWinTime.string` is already the pure one.

### IN-05: The count-up task swallows cancellation

**File:** `gamekit/gamekit/Games/Sudoku/SudokuCountUpTime.swift:46-50`
**Issue:** `try? await Task.sleep(...)` returns immediately when the task is cancelled (card dismissed, gate flipped) and the next line still writes `finished = true`. Harmless today because that is also the desired end state, but the write happens on a view that is going away.
**Fix:** `guard (try? await Task.sleep(...)) != nil else { return }`.

### IN-06: `SudokuCellView.motion` defaults to true

**File:** `gamekit/gamekit/Games/Sudoku/SudokuCellView.swift:45`
**Issue:** A second call site that forgets the argument gets ungated ripple and shake. The gate fails open.
**Fix:** Remove the default so the argument is required.

### IN-07: Stale file name

**File:** `gamekit/gamekit/Games/Sudoku/SudokuGameView+DebugTuning.swift:1`
**Issue:** The strength tuning was deleted in plan 07; the file now holds only the near-win action.
**Fix:** Rename to `SudokuGameView+DebugNearWin.swift`.

### IN-08: Restart and Next puzzle fire haptics by resetting the counters (pre-existing, outside this phase's diff)

**File:** `gamekit/gamekit/Games/Sudoku/SudokuViewModel.swift:322-345`
**Issue:** `resetSessionState()` sets `placeCount`, `completionGlowCount`, `numberCompleteCount` and `wrongAttemptCount` back to 0, and each is a `sensoryFeedback` trigger (`SudokuGameView.swift:272-287`). A change from N to 0 is a change, so Restart or Next puzzle can fire the light, medium, heavy and `.error` haptics together. The same was true at the diff base. It is noted here because 3.8's new haptic table says pressing a piece fires nothing of its own, and "Next puzzle" is now a piece. The new wave and shake triggers share the pattern but stay invisible because the step is read at trigger time.
**Fix:** Do not reset the counters; they are monotonic triggers, not session state.

### IN-09: The pad key's "digit used up" pulse still jumps with motion off (pre-existing)

**File:** `gamekit/gamekit/Games/Sudoku/SudokuNumberPad.swift:80`
**Issue:** `scaleEffect(pulsing.contains(digit) ? 1.12 : 1.0)` is unconditional; only its animation is gated. With animations off or Reduce Motion the key snaps to 112% for 350ms and snaps back, which is a pop that DESIGN.md 0 says is removed.
**Fix:** Gate the scale itself on the motion flag.
