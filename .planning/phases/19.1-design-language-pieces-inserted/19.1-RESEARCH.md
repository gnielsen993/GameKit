## Summary

Sudoku already has a quiet version of every beat the sketch shows, but each is implemented separately and none is a "piece". The pad keys are flat surface rects with a 1pt border and `chipShadow()`, using `.pressable` (scale 0.94). Erase is implemented **twice** (a 36pt circle in `SudokuGameView.swift:353`, and an inline 24pt rounded square in the large-zone Video Mode row at `SudokuGameView+VideoMode.swift:162`). The Value/Notes pill is one `Button` wrapping a capsule. The end card is `DKCard` + `DKButton`. The pad itself is **not** re-implemented for Video Mode: `SudokuNumberPad` is reused in all four layouts, and the end card is one shared `endStateOverlay`. That means the conversion surface is small: four sites, six call locations.

The correct-placement pop exists but is weak (scale-in from 0.55 inside a 0.25s spring, `SudokuCellView.swift:115`). The unit-complete glow is simultaneous, not sequenced, uses a flat 0.22 accent fill, and its animation is **inverted relative to its own comment** (slow `easeOut(0.65)` rise, 0.1s fall; and not motion-gated). A wrong placement in Lives mode shows only a red flash on an otherwise unchanged cell: despite comments and DESIGN §10.2 describing a shake, **no shake exists** in Sudoku. The win is a static success wash, a 1500ms pre-roll, then a centered `DKCard` with a static monospaced time. No count-up, no personal best.

The hardest planning constraints are not visual. (1) `SudokuViewModel.swift` sits exactly at its 696-line ratchet, and the win path needs a new "set a best" flag; the plan must first buy headroom (move the 18-line `#if DEBUG` test seam to its own file). (2) `GameStats.record(...)` returns `Void` and its `evaluateBestTime` is private, so the win path cannot know a best was set without a signature change; make `record` return a discardable result so the assist/records rule stays in one place. (3) The edge color cannot be "face darkened 32%" on dark presets: on real Dracula and Voltage dark the darkened edge is indistinguishable from the background. The edge must come from compositing `textPrimary` over the opaque surface for neutral pieces (no color math, no literal, iOS 17-safe). (4) Launch-arg `-gamekit.animationsEnabled NO` does **not** turn animations off (verified), which matters for the SC3 simulator checks.

**Primary recommendation:** Add `Core/PieceButtonStyle.swift` (+ `PieceSpec`, geometry as a pure function, shade/shadow constants in `SurfaceDepth.swift`) as a **new** `ButtonStyle` beside, not replacing, `PressableButtonStyle` (four other games still use it). Convert exactly the Sudoku pad keys, both erase implementations, the Value/Notes pill (both sizes) and the end-card buttons. Drive wave/shake from per-cell keyframe animators keyed on the existing VM counters. Return a `RecordResult` from `GameStats.record`. Keep the debug strength switch in a whole-file `#if DEBUG` store with `@AppStorage` and verify it is absent from a Release binary.

## Personal Best and Win Path (Question 3)

How a best is determined today [VERIFIED: `Core/GameStats.swift`]:
- `record(gameKind:difficulty:outcome:durationSeconds:puzzleId:assistCount:countsTowardRecords:)` inserts a `GameRecord`, then `if outcome == .win && !record.wasAssisted && countsTowardRecords { try evaluateBestTime(...) }`, then saves. Returns `Void`.
- `evaluateBestTime` is `private`; updates only on `seconds < current.seconds` ("Strictly-less-than guard"), inserts a `BestTime` when none exists.
- `GameRecord.wasAssisted` is `(assistCount ?? 0) > 0` (`GameRecord.swift:75`).
- Sudoku passes `assistCount: assistsUsed` (`SudokuViewModel.swift:662`) and does not pass `countsTowardRecords` (default true). A win in `.practiceAfterLoss` goes to `.practiceComplete` and calls **no** `record` at all (`completeBoard`, `:638-645`), so practice completions never set a best.
- `recordWin` calls it as `try? gameStats?.record(...)`, discarding any result.

**Consequence:** at the moment the end card appears the VM cannot tell whether this run set a best. By then `BestTime` already holds the new value, so a post-hoc comparison is impossible.

**Recommendation:** make the time overload of `record` return `@discardableResult RecordResult` with `setBestTime: Bool` and `previousBest: Double?`, computed inside `evaluateBestTime` (which already knows `existing.first`). Do not re-derive the rule in the VM (a second copy of "assisted / strictly faster / countsTowardRecords" will drift). Existing callers ignore the result and compile unchanged under `@discardableResult`. In `recordWin`, store `lastWinSetBest`/`previousBest` on the VM (reset in `resetSessionState`). `GameStats.swift` is 395 lines; this adds ~15 and crosses 400 (under the hard cap); put `RecordResult` in its own small file.

Semantics to settle (Open question 2): a player's first-ever win at a difficulty does create a `BestTime`, so `setBestTime == true` and `previousBest == nil`. D-09 literally says "actually set", so the badge would show on a first win. Recommended default: show it (it is true), with `previousBest` available if Gabe prefers copy such as "New best" only when `previousBest != nil`.

Tests that already exist and must keep passing: `SudokuStatsIntegrationTests` (faster win updates, slower does not) and `AssistRecordSemanticsTests` ("an assisted win is recorded but sets no best time"). New tests extend these, using `InMemoryStatsContainer.make()` (`gamekitTests/Helpers/InMemoryStatsContainer.swift`).

## Piece Primitive Design (Question 4)

### Recommendation
One `ButtonStyle`, `PieceButtonStyle`, in `Core/PieceButtonStyle.swift`, parameterised by `theme`, a `role` (`.neutral` or `.filled(Color)`), a `shape` (`AnyShape`), and a `size` (`.regular` / `.compact`). A convenience `View.pieceButton(...)`/`ButtonStyle.piece(...)` mirrors the existing `.pressable` extension. It never touches `PressableButtonStyle`.

Construction order (this order is what keeps layout stable and hits stable):

```swift
// Sketch of the structure (values come from PieceSpec, colors from theme + SurfaceDepth).
func makeBody(configuration: Configuration) -> some View {
    let spec = PieceSpec.current            // release: constants; debug: strength-backed
    let motion = settingsStore.animationsEnabled && !reduceMotion
    let down = configuration.isPressed && isEnabled
    configuration.label
        .background(face(role))                                   // 1. face fill
        .clipShape(shape)
        .overlay(down ? theme.colors.fillPressed : .clear)        // 2. static pressed cue (also when motion off)
        .offset(y: PieceGeometry.faceOffset(pressed: down, motion: motion, enabled: isEnabled, spec: spec))
        .background(alignment: .top) { edge(role).offset(y: spec.depth) }   // 3. edge, sized to the un-offset frame
        .padding(.bottom, spec.depth)                              // 4. reserve the edge in layout
        .contentShape(Rectangle())                                 // 5. STABLE hit region, applied last
        .animation(motion ? (down ? spec.pressIn : spec.release) : nil, value: down)
}
```

`PieceGeometry.faceOffset` is a pure function (`pressed`, `motion`, `enabled`, `spec` -> CGFloat): `0` when `!motion` or unpressed; `spec.travel` when pressed and motion; the disabled face sits at `spec.depth - 1` (sunk, "flat" per DESIGN §0 "things that are not pressable are flat"). Unit-testable without SwiftUI.

### Pitfalls
1. **Hit-testing jitter.** If the hit region follows the offset face, a touch on the top 2-3pt of the face leaves the region as soon as the face drops, un-presses, springs back, re-presses. Apply `.contentShape` to the outermost, un-offset frame (face + reserved edge). [ASSUMED mechanism; confirm in the Wave 0 spike by tapping the top edge of a key on the SE simulator.]
2. **No layout jump.** `.offset` is layout-neutral; the edge is reserved with `.padding(.bottom, depth)` so the pad row height is constant. The edge must be drawn **outside** the face frame via `.background` on the offset view, not as a sibling that changes the container size.
3. **`ButtonStyle` vs `PrimitiveButtonStyle`.** Use `ButtonStyle`. `isPressed` is sufficient and Button keeps accessibility traits, disabled handling and keyboard focus. `PrimitiveButtonStyle` would be needed only for custom long-press or drag behavior; none here.
4. **Disabled state.** Read `@Environment(\.isEnabled)` in the style (as `PressableButtonStyle` reads `\.settingsStore`). Exhausted keys: sunk face, edge collapsed, dim, and **keep the strike glyph** so meaning does not rest on opacity (DESIGN §10.4, §5.5).
5. **Motion gating.** Same idiom as `PressableButtonStyle.swift:26`: `settingsStore.animationsEnabled && !reduceMotion`. With motion off: no offset at all (SC3 "nothing travels"); the pressed state is the `fillPressed` overlay (a DesignKit token) so a tap still registers. This is a decision beyond the sketch; record it (A5).
6. **Press-in vs release timing.** Choose the animation from the new value: fast ease-out on press, spring on release. A short tap can release in ~60-80ms; if the press-in is slower than that the face never reaches the bottom and the tap looks dead.
7. **Spring overshoot is physically tiny at 4-6pt travel.** Underdamped overshoot fraction is `exp(-pi*z/sqrt(1-z^2))`: z=0.5 gives about 16% (0.65pt of 4pt), z=0.4 about 25% (1.0pt). So "a spring that overshoots slightly" is mostly perceived from release speed. Tune by feel; if needed encode the overshoot explicitly (rest -> -1pt -> 0) rather than lowering damping until it wobbles. [derived arithmetic]
8. **Dynamic Type.** Depth/travel are fixed points (physical), not `@ScaledMetric`. Key height grows with the label fonts (title2 + caption), which already happens; the edge adds a constant. At AX sizes Video Mode already loses the board (v1.6 audit: "At accessibility XXXL, the Sudoku board disappears", `Docs/audits/v1.6-user-audit-2026-09-08/README.md:19`); the edge must not worsen it, so give `.compact` a smaller depth.
9. **Video Mode large-zone row has a fixed height.** `largeZoneControlRow` ends with `.frame(height: theme.spacing.xl)` (`VideoMode.swift:211`) and the pill is compact (`minHeight: theme.spacing.l`). A piece that reserves 4-5pt more than the slot overflows into the VStack gap. Change that frame to `minHeight` (or add the compact depth) and re-check DESIGN §3.5 numbers. `size: .compact` should use a derived smaller depth (suggest ~60% of regular, rounded).
10. **Contact-shadow cost.** Sketch has a soft 12px blur shadow on every piece. Nine blurred shadows on the pad plus 81 keyframe-capable cells is the "no frame cost on the pad" exit criterion (ROADMAP 19.1). Start without a blur shadow on pad keys (solid edge only), keep it on the large CTA, and measure with Instruments (`xcode-integration:xctrace`). [ASSUMED cost]
11. **44pt targets.** Keys are 35pt wide on SE (see above), erase is 36pt, large-zone controls are 24pt. All pre-existing. Do not claim the piece fixes them; consider `contentShape` expansion only if cheap.
12. **The pulse composes.** `scaleEffect(pulsing ? 1.12 : 1)` stays outside the button and scales the whole piece incl. edge; keep it outside the style.

### Neutral vs filled
- `.neutral`: face `theme.colors.surface`, label `textPrimary`.
- `.filled(color)`: face is the color (selected pad key = `accentPrimary`; primary CTA = `accentPrimary`), label color `theme.colors.background` (existing convention: selected key uses `theme.colors.background`, `SudokuNumberPad.swift:51`). ## Edge Color Derivation (Question 5)

### What DesignKit exposes [VERIFIED: `DesignKit/Sources/DesignKit/Theme/Tokens.swift:3-19`]
`background, surface, surfaceElevated, border, textPrimary, textSecondary, textTertiary, accentPrimary, accentSecondary, highlight, success, warning, danger, fillPressed, fillSelected, fillDisabled`, plus `gameNumberPalette`.

**`border` is translucent in dark schemes**, so it cannot be the edge on its own. The edge must sit on an opaque base.

### What `SurfaceDepth.swift` may do [VERIFIED: `Core/SurfaceDepth.swift:19-58`; hook `color_exempt`]
It is the only file allowed `Color.black`/`Color.white`. Existing: `raisedSheen`, `shadow = Color.black.opacity(0.10)`, `chipShadow()` (radius 5, y 2), `activeGlow`. Add the piece lighting constants here (edge shade opacity, contact shadow), never in a game view or in `PieceButtonStyle.swift` itself (Core/ is hook-scanned for `Color.black`).

### Why "darken 32%" fails on dark presets (arithmetic from real anchors)
Dracula dark: `background: #282A36`, `surface: #343746` (`PresetTheme.swift:417-436`). Face (52,55,70) x 0.68 = (35,37,48) against background (40,42,54): the edge is darker than the background by about 5 levels and about 17 darker than the face. It barely reads. Voltage dark: `background #0B0820` (11,8,32), `surface #14102D` (20,16,45) x 0.68 = (14,11,31): effectively the background color; the lower edge is **invisible**, failing SC1/SC4 on a preset Gabe will check.

### Recommended derivation (no literal in game views, no color math, iOS 17-safe)
- **Neutral piece edge** = opaque `theme.colors.surface` with `theme.colors.textPrimary.opacity(k)` composited on top (k about 0.28; tune on device). This mirrors the sketch's neutral edge (`color-mix(line 78%, ink)`), is lighter-than-face on dark schemes and darker-than-face on light ones, and uses only tokens. Worked values: Dracula dark -> about (107,109,118) against bg (40,42,54); Voltage dark -> about (81,77,104) against bg (11,8,32); Classic light (surface white, textPrimary `#2A2620`) -> about (195,194,193) against bg `#F5F1E8`. [derived arithmetic from anchors]
- **Filled piece edge** = the fill with a black shade overlay from `SurfaceDepth` (opacity about 0.32, the sketch's 68% mix). Accent faces are saturated and contrast with the background on every preset checked, so darkening reads (Dracula `#BD93F9` -> about (128,100,169); Classic `#C0392B` -> about (131,39,29)).
- Label on filled pieces: `theme.colors.background`.

## Rounded Type (Question 6)

[VERIFIED: `DesignKit/Sources/DesignKit/Typography/TypographyTokens.swift:11-17`] defaults, verbatim: `titleLarge: Font = .system(size: 32, weight: .bold, design: .rounded)`, `title: Font = .title2.weight(.semibold)`, `headline: Font = .headline`, `body: Font = .body`, `caption: Font = .caption`, `monoNumber: Font = .system(.body, design: .monospaced)`. `ThemeResolver` passes `overrides?.typography ?? TypographyTokens()` (`ThemeResolver.swift:50`).

Consequences:
- `titleLarge` is **already rounded** but fixed 32pt (no Dynamic Type). The end-card headline is therefore already rounded.
- `title` (pad digits), `headline` (buttons, pill labels) are text-style fonts with no design set: these are what need rounding. `monoNumber` is monospaced (timer): must stay mono.
- All tokens are plain `Font` values; `Font` is opaque, so a design cannot be read or swapped off a token.

Recommended (least invasive, local): apply `.fontDesign(.rounded)` (View modifier, `fontDesign(_:)` documented at developer.apple.com/documentation/swiftui/view/fontdesign(_:); iOS 16.1+ per a third-party guide, my search did not return Apple's availability line, deployment target 17 is above it either way) at the label of pieces, the pill, end-card title/time, and nowhere else. It keeps token size/weight and Dynamic Type scaling. Open assumption A1: it applies to text-style fonts but is expected **not** to override fonts that carry an explicit design (`monoNumber`, `titleLarge`). That is the desired outcome but unverified; spike it (render a key, the timer and the headline, screenshot). Fallback if it misbehaves: a local `Core/RoundedType.swift` that returns `Font.system(.title2, design: .rounded, weight: .bold)` etc., still scaling with Dynamic Type.

Win-sheet time (large, tabular): `Font.system(.largeTitle, design: .rounded, weight: .heavy).monospacedDigit()`; SF Rounded supports tabular digits [ASSUMED]. DESIGN §4 says timers use `monoNumber` + `.monospacedDigit()`; the win sheet is a deliberate exception to document in §3/§4.

Do not round: board digits (`SudokuCellView.swift:105, 109` use `title.weight(.bold/.regular)`), notes, body/caption, Stats, Settings (D-06).

### Pattern: counter-triggered per-cell keyframes
**What:** Pass `waveToken: Int = completionGlowCount` and `waveDelay: Double?` into `SudokuCellView`; the cell applies `.keyframeAnimator(initialValue:trigger:)` with a hold of `waveDelay`, then rise, hold, fall of a highlight and 1.0 -> 1.08 scale; non-members run no-op keyframes. Gate with `trigger: motion ? waveToken : 0`. Same shape for the shake with `wrongAttemptCount` and `lastWrongAttemptIdx`. Pop: raise the existing transition scale from 0.55 to about 0.3 with a longer spring.
**Why this shape:** a Bool "isGlowing" re-triggers on clear; a counter does not. Matches DESIGN §8.2 and the existing VM contract. [ASSUMED keyframeAnimator trigger semantics; A3 spike.]
**Motion off:** keep the existing static `isGlowing` fill (no stagger, no scale) so the completed unit still registers (DESIGN §10.4).
**Ordering:** recommend ripple outward from the placed cell (delay by distance within the unit) rather than the sketch's index order, because it reads as caused-by-your-move (DESIGN §10.1). This is Claude's discretion (CONTEXT). Pure function, tested. Win wave: all 81 cells by Manhattan distance from the last placed cell; the largest delay (about 16 x 45ms) plus the 0.7s animation fits inside the existing 1500ms pre-roll (DESIGN §10.3).
**Clear timer:** `fireCompletionEffects` clears the set after 800ms; with staggered delays the static fallback and any set-membership reads must tolerate that, or lengthen to cover the longest delay.

## Common Pitfalls

### Pitfall 1: `SudokuViewModel.swift` cannot absorb the new state
**What goes wrong:** the win-best flag (and optionally a completion origin) are stored properties, which cannot live in extensions; the hook fails any commit growing the file past its baseline.
**Evidence:** `.githooks/file-size-baseline.txt`: `696 gamekit/gamekit/Games/Sudoku/SudokuViewModel.swift`; `wc -l` = 696.
**How to avoid:** first task moves the `#if DEBUG ... injectTestBoardForUnitTests` extension (`SudokuViewModel.swift:678-695`, writes only `currentPuzzle`, `board`, `lockedCells`, all internal `var`s) into `SudokuViewModel+TestSeam.swift`. That frees ~18 lines; run `scripts/refresh-size-baseline.sh` so the ratchet tightens. Net property additions must stay below the freed amount.
**Warning signs:** pre-commit "grew to N lines, over its baseline of 696".

### Pitfall 2: animations cannot be switched off by launch argument
**What goes wrong:** `SettingsStore` reads `(userDefaults.object(forKey: Self.animationsEnabledKey) as? Bool) ?? true` (`SettingsStore.swift`). A launch argument arrives as a string, so `as? Bool` is nil and the default `true` wins.
**Evidence:** [VERIFIED by running a Foundation test binary this session] `-gamekit.animationsEnabled NO` -> `object: Optional(NO)`, `as Bool: nil`, `bool: false`; `0` and `false` also nil; `'<false/>'` -> `as Bool: Optional(false)`.
**How to avoid:** in XCUITest pass `"-gamekit.animationsEnabled", "<false/>"`. Other booleans in this repo use `bool(forKey:)` (e.g. `VideoModeStore`, `gamekit.videoModeEnabled`), so `YES`/`NO` works for those.

### Pitfall 3: "complete" is "filled", not "correct"
In Free mode a full row holding a wrong digit glows and fires the milestone haptic. A sequenced celebration over a wrong row is misleading. Gate the wave on the unit containing no `incorrectCellIndices` (the set is empty in Lives mode, so Lives is unaffected). This changes existing haptic behavior slightly; flag to Gabe.

### Pitfall 4: the existing glow animation is inverted and ungated
Replace it, do not extend it (see Feedback table). Leaving the ungated `.animation` in place violates SC3 on its own.

### Pitfall 5: end-card copy and DESIGN.md contradictions
`SudokuEndStateCard.swift` header comment says "Try again" but code says "Keep solving". DESIGN §3.6 says "Primary CTA is ALWAYS a single `DKButton`" and §3.7 "`DKButton`-style actions". The piece CTA contradicts §3.6, and DESIGN.md wins on conflicts, so the DESIGN.md amendment (Sudoku end card, until Phase 20.1) must land in the same change.

### Pitfall 6: the practice-complete card shows the same title twice
In `.practiceComplete` the primary label is "Retry this puzzle" (`:112`) and `onRetry` is nil there (`SudokuGameView.swift:182` only sets it for `.gameOver`), so no duplicate in practice. Noted only so the planner does not "fix" it.

### Pitfall 7: Reduce Motion cannot be flipped by launch argument
Use the simulator Accessibility setting or the device. `[ASSUMED]` that `xcrun simctl spawn <udid> defaults write com.apple.Accessibility ReduceMotionEnabled -bool true` works (needs a simulator restart); otherwise toggle in-sim Settings. Not verified this session. SC3 is therefore partly manual.

## Code Examples

### Pure geometry (testable, no SwiftUI)
```swift
// Core/PieceSpec.swift  (sketch; names are proposals)
struct PieceSpec: Equatable {
    var depth: CGFloat
    var travel: CGFloat
    var response: Double
    var damping: Double
}
enum PieceGeometry {
    /// Offset of the face from its rest position.
    static func faceOffset(pressed: Bool, motion: Bool, enabled: Bool, spec: PieceSpec) -> CGFloat {
        guard enabled else { return max(0, spec.depth - 1) }   // disabled = flat, sunk
        return (pressed && motion) ? spec.travel : 0
    }
}
```

### Wave ordering (pure, ripple from the placed cell)
```swift
// Games/Sudoku/SudokuCompletionWave.swift (sketch)
enum SudokuCompletionWave {
    /// index -> step (0 = placed cell). A cell in several completed units takes its smallest step.
    static func steps(origin: Int, completed units: [[Int]]) -> [Int: Int] {
        var out: [Int: Int] = [:]
        for unit in units {
            guard let o = unit.firstIndex(of: origin) else { continue }
            for (i, cell) in unit.enumerated() {
                out[cell] = Swift.min(out[cell] ?? .max, abs(i - o))
            }
        }
        return out
    }
}
```
